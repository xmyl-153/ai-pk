# 19 个测量缺陷（本项目的"免疫系统"）

> **这个项目最有复用价值的部分不是榜，是这份清单。**
>
> 共同点：**每一次"某个模型表现异常差"或"某个指标好得不真实"，查下去都是测量代码的问题。**
> 每一修都配了回归测试（`tests/test_measurement.py`），防止同样的坑再踩一次。
>
> 如果你也在做评测：把这份清单当成自检表，逐条问自己"我这儿有没有这个坑"。

| # | 缺陷 | 当时的表现 | 修法 |
|---|---|---|---|
| 1 | 不限速被网关 429 打成假 0 分 | GLM-5.3 被误判 5/24 | 每网关限速 1.2 QPS + `infra_failure` 排除出评分 |
| 2 | 触发输入用字符串比对 | cascade 族 24/24 全灭，其实模型全答对 | 改 AST 语义归一 |
| 3 | `reps` 和实例 seed 绑死 | 每个实例只跑一次，pass^k 退化成成功率、一致性恒为 0 | 实例集固定，reps 是对**同一实例**重复跑 |
| 4 | 跨 profile 比较用 `.get(m, 99)` | 没跑过的模型算出 97 位假漂移 | 只比较跨全部 profile 都有的模型 |
| 5 | 关键字写法落在 `node.keywords` 而非 `node.args` | `items=[...]` 类回答全判错 | 两边都收 |
| 6 | **多参数加圆括号多包一层** | `([7,1,4,1,9],2)` vs `nums=[...],k=2` 差一层 → **10 个模型全被冤枉** | 递归摊平嵌套元组 |
| 7 | **builder 把 `repr(list)` 拼进列表字面量** | 题目自己给出 `nums=[[...]]` 双层嵌套，模型答对反被判错 | 改用 f-string；加"触发输入自洽性"测试 |
| 8 | 网关流式不报 usage 当 0 | 该模型被算成零成本，成本指标失真 | 用字符数估算并标 `≈` |
| 9 | 裁判 `max_tokens=2048` 被 reasoning 吃光 | writing 族盲评全返回 null | 提到 6144 + 失败重试 + 记无效率 |
| 10 | 隐藏用例用 JSON **字符串**比较 | 模型把 `return 0.0` 等价改成 `round(max(amount-paid,0),2)`（返回 int 0）被判"没修对" | 改**数值语义比较**：0 == 0.0 |
| 11 | 外部 harness 把协议文件写进任务工作区 | 三个**完全正确**的最小修复被算成"牵动 32 行、3 个文件"→ 全判失败 | 协议文件移出工作区 + `PROTOCOL_ARTIFACTS` 排除名单 |
| 12 | 分阶段族的"没给出 JSON"提前返回 | 把"会话中途停住"显示成"格式不对"，真实信号被埋 | 区分「会话没走完」与「格式不对」，理由里给阶段进度 |
| 13 | **HTTP 400 参数不被接受，被算成模型答错** | 给 kimi-k3 传 `temperature=0.7` 被网关 400 拒绝 → 那一轮 **18/18 全灭、pass^k 0%** | 参数类 400 一律不算模型失败 + 自动降级重投 + 报告标注「参数降级」 |
| 14 | 裁判模型名写错 → 盲评**静默消失** | `_split_key` 只认 `provider/model`，写裸模型名抛异常被吞成"裁判不可用" | 支持裸模型名 + 解析失败大声告警，不再静默继续 |
| 15 | "裁判不评自己"的判据没归一化 | 裸名与运行记录 key 不相等 → 排除静默失效，**裁判给自己的答案打了分** | 排除判据改用归一化 key（回归测试锁死） |
| 16 | **裁判"没判出来"被当成平局** | 一次有效裁决都没有时 winner 默认 `tie` → 折算 **0.5 分**，裁判罢工反而白送半分 | 显式标 `invalid`，不写分数、只记无效；审计算进无效率 |
| 17 | **多裁判重评的判决键少了模型维度** | 键 `(题, rep, 裁判)` → 同格 10 个模型共用一条判决：**分数全一样、Kendall τ 假模假样 =1.000** | 键加 `model_key`；这类"收敛得漂亮"的结果比崩掉更危险 |
| 18 | 饱和诊断的"族数"判据会误判整体饱和 | "5 族里 2 族饱和、3 族仍有区分度、极差 25pp"也被判**整体饱和** —— 而这是报告标题级结论 | 改成两条明确理由（极差 <15pp / 没有任何族能分开模型）并写进报告 |
| 19 | **离线机器人的任务状态存在实例属性里（并发串题）** | Runner 对每个模型只建一个 provider 实例、多线程共用 → A 题的答案被 B 题取走，满分机器人只过 **92.3%**；**单线程/低并发完全看不出来**，是"换目录跑一次 13 题"才撞出来的 | 任务状态改放 `threading.local()`；补并发回归测试（并用旧实现验证该测试会红） |

### 附带教训：测试自己也要被验证（缺陷 #19 的续集）

补完并发测试后，我干了一件必须干的事：**把旧的有 bug 的实现拿出来，看这个测试会不会红**。
结果 —— **第一版测试在坏代码上也是绿的**：

```python
# ❌ 第一版：4 个线程各跑一批任务
def worker(chunk):
    for t in chunk:
        prov.set_task(t)      # set_task 与 chat 之间窗口太窄，
        prov.chat(...)        # GIL 下几乎撞不上 → 坏实现也能过
```

改成"用 barrier 强制所有线程都 `set_task` 完，才允许 `chat`"之后：
**旧实现 11 道题错 7 道（必红）、新实现 0 道错（必绿）** —— 这才算一个有效的测试。

> **规则：任何防回归的测试，都要拿"已知有 bug 的版本"跑一遍确认它会红。**
> 抓不到 bug 的测试比没有测试更糟 —— 它给你虚假的安全感。

## 从这 18 条里提炼的通用规则

1. **模型异常差 → 先怀疑测量。** 至少在我这儿，18 次里 18 次都是测量代码的问题。
2. **能语义比就别字符串比。** 数值、列表、JSON 结构、代码表达式，全部要归一。
3. **题目自己也要被测。** "参考答案必须被判对"应写成测试（`selfcheck`），
   而不是靠肉眼看报告。
4. **静默失败最贵。** 盲评消失、裁判罢工、参数被忽略 —— 这些不报错的失败比崩溃危险得多，
   一律要"大声告警 + 报告里标注"。
5. **键要带全维度。** 少一个维度（比如模型）不会崩，只会让结果变得"很整齐"——最危险的一种错。
6. **门禁要便宜。** `python -m aipk demo` 不需要 key 就能跑通全链路：
   花了钱才发现装置坏了，是最贵的一种失败。
7. **实验前先验证仪器。** 想测方差？先用 `tools/probe_temperature.py` 确认
   `temperature` 真的生效、确认 `temperature=0` 并不是确定的。
8. **测试自己也要被验证。** 任何防回归测试，都要拿"已知有 bug 的版本"跑一遍确认它会红
   （见下面缺陷 #19 的续集）。
9. **"在我机器上是好的"不算数。** 换一个工作目录、换一个并发度、换一次干净 clone，
   都要能跑通 —— 缺陷 #19 就是这么被抓出来的。
